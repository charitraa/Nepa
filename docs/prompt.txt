# Build a New Programming Language from C

You are a senior compiler engineer, programming-language designer, runtime engineer, and C systems programmer.

I want to create a **real programming language from scratch**, implemented primarily in **C**.

The goal is to build a language that is:

* Fast and compiled
* Simple like Python
* Structured and scalable like Java
* Low-level capable like C
* Easy for Nepali developers to read
* Uses a mixture of English and romanized Nepali
* Suitable for real applications, not just a toy language
* Eventually capable of enterprise-scale software
* Designed with a clean syntax that can evolve without breaking the language

The language should initially compile/run on Linux x86-64.

---

# 1. Core Language Philosophy

The language should feel natural to a Nepali programmer.

Use **romanized Nepali words** for common programming concepts while keeping technical concepts understandable.

Examples:

```text
vana("Namaste")
```

Meaning:

```text
print("Namaste")
```

Other possible keywords:

```text
vana        = print
leu         = input/read
yedi        = if
natara      = else
jabasamma   = while
ko_lagi     = for
kaam        = function
farkau      = return
sacho       = true
jutho       = false
khali       = null
banau       = create
class       = class
interface   = interface
import      = import
```

Do NOT blindly translate every English programming keyword.

The language should use Nepali where it improves readability, while keeping common technical concepts in English when appropriate.

The language should feel like:

```text
Nepali thoughts
+
English technical concepts
```

Example:

```text
kaam main() {
    naam = "Charitra"

    yedi naam == "Charitra" {
        vana("Namaste " + naam)
    }
}
```

```text

```

Never create a huge codebase without testing each stage.

# 4. Implementation Language

The compiler/interpreter must initially be written in:

```text
C
```

Use modern C where practical.

Prefer:

```text
C11/C17
```

Use:

* structs
* pointers
* dynamic memory
* enums
* function pointers where useful
* modular `.c` and `.h` files
* clear ownership rules
* error handling
* memory-safe practices

Avoid unnecessary dependencies.

Build the language using this architecture:

```text

     ↓
```

```text

```

The architecture must allow this evolution without rewriting everything.

# 8. Version 0.3 — Nepali-English Control Flow

Design readable syntax.

Example:

```text
yedi umar >= 18 {
    vana("Adult")
} natara {
    vana("Minor")
}
```

Loops:

```text
jabasamma umar < 25 {
    umar = umar + 1
}
```

For loop:

```text

    vana(i)
}
```

The syntax must remain unambiguous to the parser.

# 11. Version 0.6 — Structures / Classes


Usage:


Support:

* fields
* methods
* constructors
* encapsulation
* inheritance only if it provides real value

Do not copy Java's complexity unnecessarily.

# 12. Scope

Implement lexical scoping.

Example:

```text

kaam test() {
    x = 20
    vana(x)
}

vana(x)
```

The language must correctly distinguish local and global variables.

Use a proper symbol table.

# 13. Symbol Table

Implement the symbol table using an efficient hash table.

It should store information such as:

```text

type
scope
location
constant/mutable
function/class information
```

Example:

```text

    type: int
    scope: local
```

The compiler must produce useful errors for:

```text

duplicate declaration
wrong scope
invalid assignment
```

# 29. Development Rules

Follow these rules strictly:

1. Keep the implementation small.
2. Do not over-engineer.
3. Do not implement future features prematurely.
4. Keep compiler phases separated.
5. Avoid global state where possible.
6. Use clear C structures.
7. Check every allocation.
8. Free allocated memory correctly.
9. Add tests before moving to the next major feature.
10. Explain important compiler concepts while implementing them.
11. Never generate thousands of lines of code at once.
12. Implement one subsystem at a time.
13. Compile after every meaningful change.
14. Fix compiler warnings.
15. Use sanitizers during development.
16. Keep the language grammar documented.
17. Keep syntax backwards-compatible whenever possible.
